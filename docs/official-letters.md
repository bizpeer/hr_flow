# 회사별 서류 작성·결재·PDF 발급

`서류 발급`은 공문·재직증명서·경력증명서를 같은 회사 템플릿과 번호 체계로 관리합니다. 기본 경로는 `/documents`이며 기존 `/official-letters` 주소와 알림 링크도 유지합니다. 이번 서류 확장은 기존 휴가·근태 기능과 지출결의의 1단계 승인 방식을 변경하지 않습니다.

## 사용 순서

1. 회사 관리자 **ADMIN**이 `서류 발급 → 회사 서류 템플릿`에서 회사명·영문 회사명(선택)·주소·대표자·로고·인감을 등록합니다. 이미지 형식은 PNG/JPEG, 최대 300KB·4096px입니다. 전화·이메일도 함께 보관하며 세 종류의 서류에서 공통으로 사용합니다.
2. 최초 등록 때 마지막으로 발행한 문서번호의 앞 세 자리 순번을 입력합니다. 처음 발행하는 회사는 `000`입니다.
3. 조직관리에서 팀장(`teams.leaderId`)과 본부장(`divisions.headId`)을 지정합니다. 작성자 소속의 팀장·본부장이 순서대로 결재라인에 자동 배정됩니다. 겸직자는 한 번만 배정하고, 작성자 본인과 ADMIN은 중간 결재에서 제외합니다.
4. 모든 회사 사용자가 서류 종류를 선택하여 작성하고 **초안 저장** 후 제출할 수 있습니다. 공문은 수신·참조·제목·본문·붙임 목록을, 증명서는 대상자의 인적사항·근무기간·용도·담당자 정보를 입력합니다. 저장한 서류의 종류는 변경할 수 없으므로 다른 종류는 새로 작성합니다.
5. **ADMIN이 본인 작성 서류를 제출하면 즉시 승인·발급**됩니다. 초안 저장만으로는 발급되지 않습니다. 이때 자동 결재라인은 별도로 기록하며 중간 결재자가 직접 서명한 것으로 처리하지 않습니다. ADMIN이 다른 사람의 서류를 수정·제출하는 경우에는 순차 결재를 유지합니다.
6. 그 외 서류는 지정 결재자가 순서대로 승인한 후 ADMIN 또는 최종 승인 권한을 위임받은 같은 본부의 SUB_ADMIN이 승인합니다. 위임된 SUB_ADMIN은 자기 서류를 최종 승인할 수 없습니다. 최종 승인 시 번호와 한국 현재 날짜를 확정하고 비공개 PDF를 생성·보관합니다. 승인된 현재 개정본만 다운로드·열기·인쇄할 수 있습니다.
7. 한 번 발행된 서류는 회사 ADMIN만 수정할 수 있습니다. 수정·재배정 전 내용을 보관하고 새 개정번호를 부여하며 모든 기존 승인과 현재 PDF 연결을 초기화합니다. 새 개정본은 다시 제출·승인해야 합니다.
8. 수정 전 보관본은 ADMIN 전용 보관함에서 확인·영구 삭제합니다. 이전 PDF를 먼저 삭제하고 보관 이력을 제거하며, 파일 삭제 실패 시 이력을 남겨 재시도할 수 있습니다. 이미 발행한 번호의 예약은 유지합니다. 작성본 미리보기에는 인감을 표시하지 않으며 브라우저 인쇄도 숨깁니다.

플랫폼 `SUPER_ADMIN`은 회사 서류 승인자가 아닙니다. 서류 목록·내용·PDF는 같은 회사의 작성자·지정 결재자·ADMIN과 유효한 범위의 위임 승인자에게만 공개합니다. 부서관리자의 최종 승인 위임은 ADMIN이 `회사 서류 템플릿`에서 본부가 지정된 활성 SUB_ADMIN에게만 부여·회수할 수 있습니다. 회사정보·로고·인감·문서번호 설정·발행본 수정·이력 삭제 권한은 위임하지 않습니다.

## 증명서 작성과 조회

- 재직증명서·경력증명서는 한글/영문 성명, 생년월일(선택), 주소, 소속, 직위, 입사일, 제출 용도, 담당부서·담당자·연락처를 한영 병기 표 양식으로 표시합니다. 회원정보의 본인 성명·주소·입사일·소속을 기본값으로 사용하고 누락된 항목은 직접 입력합니다. 참조 문서의 개인정보를 기본값으로 복사하지 않습니다.
- 재직증명서는 종료일 없이 현재 재직 중으로 표시합니다. 경력증명서는 퇴사일을 입력해야 합니다. 날짜는 과거 또는 오늘이어야 하며 근무 종료일은 시작일보다 앞설 수 없습니다. 생년월일을 입력했다면 입사일보다 늦을 수 없습니다.
- 서류함에서 종류를 필터링하고 번호·제목·대상자·작성자를 검색합니다. 결재 관리함의 서류 승인 목록에서 현재 결재할 서류를 열 수 있고, 대시보드의 본인 발급내역에서 작성한 서류의 발급 상태와 PDF를 확인합니다.
- PDF 저장이 일시적으로 실패해도 승인·번호는 중복 발급하지 않습니다. 화면의 PDF 다운로드·열기·인쇄로 생성을 다시 시도합니다. 기존 발행본은 처음 다운로드할 때 비공개 PDF를 생성·보관하며 기존 내용·번호를 유지합니다.
- 기존 공문 데이터의 `documentType`이 없으면 `OFFICIAL`로 해석합니다. 기존 문서·첨부·결재라인을 일괄 변환하지 않습니다.

## 번호 규칙

- 예: `001-261105`, 날짜 표기 `2026년 11월 5일`. 뒤 여섯 자리는 `YYMMDD`이며 월·일은 각각 두 자리입니다.
- **앞 세 자리 순번만 새 발행마다 증가**합니다. 날짜나 연도가 바뀌어도 카운터를 초기화하지 않습니다. 수정본의 재발행도 새 번호를 받습니다.
- 최초 시작점은 회사 템플릿에 한 번 등록합니다. ADMIN은 최종 승인 창에서 앞 세 자리 순번만 직접 지정할 수 있습니다. 발행일은 서버에서 `Asia/Seoul`의 실제 최종 승인일로 확정하며 임의의 과거·미래 날짜를 허용하지 않습니다.
- 자동 번호는 마지막 최대 순번 다음부터 부여합니다. 수동으로 작은 번호를 지정해도 자동 카운터를 낮추지 않습니다. 같은 회사의 동일한 전체 문서번호는 재사용할 수 없습니다.
- 999를 초과하면 자동 발행을 중단합니다. ADMIN이 사용하지 않은 번호를 직접 지정해야 합니다. 네 자리 번호나 연도별 초기화가 필요하면 정책을 확장해야 합니다.
- 화면의 예상 번호는 확정 번호가 아니며, 최종 승인 시 Firestore 트랜잭션에서 원자적으로 확정합니다. 자정이나 동시 발행으로 예상값과 달라질 수 있습니다.
- 기존 `001-261023-025` 형식으로 발행된 공문과 수정 전 보관본은 그대로 유지합니다. 기존 순번 카운터를 이어받고 `lastSerial`은 더 이상 사용하지 않습니다. 동일 순번·날짜의 과거 세 부분 번호도 확인하여 수동 지정으로 중복 발행되지 않게 합니다.

## 결재 알림과 결재자 재배정

- 화면 왼쪽 알림 종에서 내 공문의 최신 알림 20개를 실시간으로 확인합니다. 미확인 배지는 100개 이상이면 `99+`로 표시합니다. 공지사항 게시판으로 이동하는 기존 동선도 유지합니다.
- 결재 요청 시 현재 차례의 중간 결재자에게, 중간 결재가 끝나면 회사 ADMIN과 같은 본부의 유효한 위임 승인자에게 알립니다. 반려·내용 수정은 작성자에게, 최종 발행은 작성자와 현재 결재자에게 알립니다.
- 알림은 앱 안에서 제공하며 메일·외부 브라우저 푸시를 발송하지 않습니다. 공문별 최신 상태 한 건을 보관하고 클릭하면 서버에서 읽음 처리한 후 해당 공문을 엽니다. 같은 공문의 새 알림도 최신 개정본을 다시 불러옵니다.
- 오류·오프라인 상태는 미확인 0개로 표시하지 않고 별도 안내와 재연결을 제공합니다. 최근 목록과 미확인 개수는 별도 제한 쿼리로 조회하므로 오래된 미확인 알림도 배지에 반영됩니다.
- 승인 권한 위임을 회수하면 서류 접근은 즉시 차단하고 기존 위임 결재 알림도 설정 저장 후 정리합니다. 정리 시 현재 권한과 알림을 다시 확인하여 새 위임·재배정 알림은 보존합니다. 정리 실패나 처리 도중 일반 안내가 남아 있어도 클릭·읽음 처리·내용·PDF 접근은 현재 서버 권한을 검사합니다.
- 회사 ADMIN은 공문 상세의 **결재자 재배정**에서 같은 회사의 활성 구성원을 최대 10명까지 선택하고 순서를 변경할 수 있습니다. 작성자·회사 ADMIN·퇴사자·타사 사용자·중복 사용자는 중간 결재자로 지정할 수 없습니다. 재배정 사유는 필수입니다.
- 재배정 전 전체 내용과 결재라인은 보관하고 개정번호를 증가시키며 모든 기존 승인을 초기화합니다. 결재 대기 공문은 대기를 유지하고 새 차례의 결재자에게 알립니다. 발행된 공문은 작성 중으로 돌아가므로 재요청·재승인 전에는 PDF를 생성할 수 없습니다.
- 제거된 결재자의 현재 공문 접근권한과 알림은 동일 트랜잭션에서 회수합니다. 새 결재자에게는 지정 사실을, 새 첫 결재자에게는 결재할 차례를 알립니다. 중간 결재자 없이 최종 승인권자가 직접 승인하는 라인으로 바꾸는 경우 화면에서 확인합니다.
- 배포 이전에 대기 중이던 공문도 재배정하거나 결재를 다시 요청하면 새 알림 흐름이 적용됩니다. 이전 발행본을 일괄 변경하거나 과거 이벤트 알림을 발송하지 않습니다.

## 저장·보안 구조

- `officialLetters`: `documentType`(`OFFICIAL`/`EMPLOYMENT`/`CAREER`), 현재 내용·증명서 항목·개정·상태·작성자·결재라인·최종 승인·PDF 준비 정보.
- `officialLetters/{id}/history`: 수정 전 전체 스냅샷. 클라이언트의 직접 덮어쓰기·삭제를 허용하지 않습니다.
- `officialLetterSettings`: 회사 공통 템플릿·영문 회사명·위임 승인자 ID 목록(`documentApproverIds`)과 카운터·설정 버전.
- `officialLetterNumbers`: 회사별 번호 중복 방지 예약. 보관본 삭제와 별도로 유지합니다.
- `officialLetterNotifications/{uid}/items/{letterId}`: 수신인·회사·수신 당시 역할로 제한된 알림. 브라우저는 본인 알림만 읽고 모든 쓰기·읽음 처리는 callable로 수행합니다. 계정·회사·역할 변경 시 화면의 이전 알림 상태를 즉시 초기화합니다.
- Storage `companies/{companyId}/official-assets/{sha256}.{png|jpg}`: 로고·인감의 변경 불가능한 콘텐츠 주소. 공개 다운로드 URL을 발급하지 않습니다.
- Storage `companies/{companyId}/official-pdfs/{letterId}/{revision}-{number}.pdf`: 최종 승인된 PDF의 비공개 원본. 클라이언트의 직접 읽기·쓰기를 차단하고 인증·현재 승인 상태를 확인한 callable로만 반환합니다. 보관본 삭제 시 해당 개정의 PDF도 제거합니다.
- 모든 공문 API는 `manageOfficialLetters` callable 하나로 처리합니다. 인증 프로필의 현재 역할·활성 상태·회사 소속을 서버에서 확인하고, 브라우저의 역할 값과 작성자·결재자 주장을 신뢰하지 않습니다.
- Firestore·Storage 보안규칙은 공문 내용·인감·번호 경로의 모든 클라이언트 직접 접근을 차단합니다. 알림은 활성 회사의 본인·현재 역할이 일치할 때만 직접 읽기를 허용합니다. 기존 SUPER_ADMIN wildcard에서도 공문·알림 경로를 제외합니다.
- 결재 요청 당시 회사명·주소·대표자·로고·인감 경로를 고정합니다. 이후 회사 템플릿을 변경해도 해당 결재본과 발행 PDF는 바뀌지 않습니다. ADMIN 최종 승인 화면은 요청 당시의 인감을 표시합니다.
- 동시 수정·재배정은 개정번호로, 회사 템플릿 저장은 설정 버전으로 충돌을 검사합니다. 수정·재배정·중간 승인·최종 승인·번호 예약·알림 변경은 서버 트랜잭션으로 처리합니다. 알림 읽음 처리도 현재 공문 접근권한과 알림 갱신 시각을 다시 확인합니다.
- PDF는 저장된 승인 스냅샷과 Noto Sans KR 글꼴을 사용해 서버에서 생성·보관합니다. 저장본을 재사용하거나 새로 생성한 경우 모두 현재 개정·승인·사용자 권한을 다시 검사합니다. 원본 인감 데이터는 ADMIN에게만 반환합니다.
- 본문은 일반 텍스트와 줄바꿈을 지원하며, HTML을 실행하지 않습니다. 긴 본문은 A4 여러 페이지로 나누고 각 페이지에 문서번호·개정·페이지 번호를 표시합니다.

## 검증

Node.js 24 기준입니다. 테스트는 `FIRESTORE_EMULATOR_HOST`가 없으면 실행을 거부하므로 운영 DB를 대상으로 실행할 수 없습니다.

```powershell
npm --prefix client run build
npx firebase-tools emulators:exec --only firestore,storage --config firebase.security-test.json --project demo-hr-flow "npm run test:official-letters && npm run test:rules"
npm --prefix client run test:payroll
npm --prefix functions audit --omit=dev
```

서류 테스트는 실제 Firestore 에뮬레이터의 트랜잭션을 사용하고 Storage만 메모리 대역으로 처리합니다. 보안규칙 테스트는 실제 Firestore·Storage 에뮬레이터를 사용합니다. 세 종류의 양식·증명 기간, 동시 번호 발행·현재 발행일·기존 번호 보존·중복·소진, ADMIN 본인 서류 자동 발급과 순차 결재·위임 범위·본인 최종 승인 차단·권한 회수, 재배정·이력·알림 격리, 발행본 수정·재승인, 비공개 PDF 보관·재생성과 한글 PDF를 검사합니다.

한글 글꼴은 `functions/fonts/`에 포함하며 OFL 라이선스를 함께 보관합니다. PDFKit 공식 문서: <https://pdfkit.org/docs/text.html>. 번호 발행 트랜잭션 원칙: <https://firebase.google.com/docs/firestore/manage-data/transactions>.

## 운영 반영

웹은 GitHub main 푸시로 Cloudflare Pages가 배포합니다. **Firebase 백엔드는 별도 배포가 필요**합니다. 아래 명령은 Firebase Hosting이나 기존 다른 Functions를 배포하지 않습니다. 운영 Firebase 배포는 담당자의 명시적 승인을 받고 실행합니다.

```powershell
npx firebase-tools deploy --only functions:manageOfficialLetters,firestore:rules,firestore:indexes,storage --project weberp-8f25f
```

`firestore.indexes.json`에는 확인 당시 운영 중인 attendance·공문 인덱스와 알림 목록/미확인·기존 번호 충돌 검사 인덱스를 포함합니다. 운영에서 수동 추가한 인덱스가 있다면 배포 전에 목록을 대조하여 보존해야 합니다. 새 인덱스의 준비 완료 후 웹을 반영하고 실제 회사 테스트 계정으로 세 종류 작성 → 순차 결재 → ADMIN/위임 SUB_ADMIN 최종 승인 → PDF 발급, ADMIN 본인 서류 제출 즉시 발급, 대시보드·결재함 연결, 결재자 재배정과 알림 클릭을 확인합니다.

후속 서비스 개발 단계로 공문함 페이지 단위 조회, 네 자리 순번 정책, 보관 기간·미사용 인감 자산 정리 정책을 권장합니다.
